Build a mobile-first ride-hailing app for Rwanda called MotoLink (or placeholder name). The app has two sides: Customer and Rider. There is no price suggestion from the platform — pricing is always negotiated directly between customer and rider, reflecting Rwanda's bargaining culture. Once both parties agree on a price verbally (via call/text), they each enter the agreed amount in the app to confirm the booking.

CUSTOMER SIDE
Onboarding:

Sign up: full name, phone number (OTP verification), email, password
Login: credentials stored after first login (persistent session, no repeated logins)

Home / Booking Flow:

On app open, show a map with available bikes/vehicles nearby
Customer sets pickup (current location via GPS or manual pin) and destination — like Uber's input UI
Vehicle type selector: Moto (motorcycle), Cab (car), Pickup Truck (cargo)
After selecting vehicle type, show available riders on the map as pins
Tapping a rider pin shows: rider name, photo, vehicle plate, rating, and a Call / SMS button
Customer contacts rider directly to negotiate price
After verbal agreement, customer enters the agreed price in the app to confirm the booking
Once confirmed: live tracking of the rider's distance and ETA to the customer
After ride: customer can rate the rider


RIDER SIDE
Registration (admin-assisted or self-registration):

Full name, phone number (OTP), national ID number, home address
Vehicle type, license plate number
Document uploads: national ID photo, vehicle registration, driver's license
Account pending approval state before going live

Rider Home / Job Flow:

Rider sees a map showing customers who have reached out (only those who contacted them)
Customer card shows: name, pickup location, destination, distance from rider
Rider can tap a customer to see route preview to their pickup point
After call/negotiation, rider enters the agreed price in the app to confirm acceptance
Only confirmed/mutually agreed rides are shown as active bookings
Rider can rate the customer after the ride


SHARED / SYSTEM FEATURES

Real-time map with live location updates (mock data ready for real WebSocket/API swap)
In-app call and SMS deep links (tel: and sms: links)
Ride status flow: Searching → Contacted → Price Agreed → Rider En Route → Arrived → In Transit → Completed
Push notifications: new customer request, ride confirmed, rider arrived
Ratings and reviews (both directions: customer rates rider, rider rates customer)
Ride history for both sides
Basic profile management (photo, name, phone)


TECHNICAL REQUIREMENTS

Use mock data throughout but architect all API calls cleanly (service layer / repository pattern) so real backend endpoints can be swapped in with minimal changes
Map: mock location data simulating Kigali, Rwanda coordinates
Auth: mock OTP flow with a hardcoded code (e.g. 1234) for testing
State management: clean separation of UI state and data state
Design: clean, intuitive, extremely easy to use for non-technical users in Rwanda; minimal text, icon-driven where possible, works well on low-end Android devices
Language: English UI (Kinyarwanda-ready string structure for future localization)
